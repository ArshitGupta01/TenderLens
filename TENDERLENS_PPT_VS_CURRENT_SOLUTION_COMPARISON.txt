3. SLIDE-BY-SLIDE DETAILED GAP & EVOLUTION ANALYSIS
----------------------------------------------------------------------------------------------------

=== SLIDE 1: Title & Positioning ===
* PPT Vision:
  - Title: TenderLens: AI-Powered Tender Qualification & Disqualification Engine.
  - Positioning: "From fragmented tender documents to evidence-backed Bid / No-Bid decisions."
  - Guiding Rule: "Proposed system -> Human review for ambiguous cases."
* Current Solution Realization:
  - Fully maintained the core identity and positioning.
  - Preserved the human-in-the-loop review architecture via Safe Uncertainty.
  - Evolved tagline: "Don't just find tenders. Know what needs to be verified before you bid."

=== SLIDE 2: Problem Statement ===
* PPT Identified Core Pains:
  1. Fragmented tender information across Main Tender PDF, Linked ATCs, and Corrigenda.
  2. Hidden eligibility conditions and mandatory certificates.
  3. Turnover / exemption traps (MSME waivers revoked by buyers).
  4. Portal access friction and capital locked in EMD deposits.
* Current Solution Realization:
  - Every single identified problem has an isolated, verified algorithmic countermeasure:
    * Hidden ATCs -> Solved via PyMuPDF low-level annotation hyperlink harvester.
    * Corrigenda overrides -> Solved via Precedence DAG Engine (Rank 1 overrides Rank 5).
    * Turnover traps -> Solved via Python-checked MSE PPP-2012 / GFR Rule 173(i) gate.
    * EMD Exposure -> Solved via GFR Rule 170(i) exemption check & Pillar D Surety Bond engine.

=== SLIDE 3: Proposed Solution (The 5-Step Pipeline) ===
* PPT Proposed Pipeline:
  - Step 01: Bidder Profile (Entity type, turnover, certs, experience).
  - Step 02: Tender Discovery (GeM, CPPP, PSU, State Portals via TinyFish Search).
  - Step 03: Deep Ingestion (Main PDF, Linked ATCs, Corrigenda, preserve page refs).
  - Step 04: Hybrid Verification (Python rules + LLM analysis + identify disqualifiers).
  - Step 05: Qualification Scorecard (Strong Bid, Conditional Bid, Red Flag with citations).
* Current Solution Realization:
  - Step 01 implemented in contracts/schema.py (BidderProfile) and Supabase user profile.
  - Step 02 implemented in TinyFishService (TinySearch) with live Tavily fallback.
  - Step 03 implemented in DocumentProcessor (PyMuPDF) and TinyFetch recursive crawler.
  - Step 04 implemented in DeterministicGatekeeper and QualificationEngine.
  - Step 05 implemented in QualificationScorecard outputting structured JSON and frontend UI.
  - Evolutionary Leap: Once Step 05 finishes, the current solution triggers the 5 Strategy Pillars 
    rather than stopping at a passive score.

=== SLIDE 4: Target Users ===
* PPT Target Audiences:
  - MSMEs & OEMs (turnover eligibility, MII local content, certifications).
  - EPC Contractors (past-project experience criteria, financial capacity).
  - IT Companies & System Integrators (scope, certifications, OEM MAF).
  - Bid Consultants (multi-client handling, automated client-wise reports).
* Current Solution Realization:
  - Built specific gates for each user group:
    * MSME: GFR 170 EMD exemption, GFR 173(i) turnover waiver, DPIIT Startup relaxation.
    * EPC: CPWD 80/50/40 similar work experience rule over 7-year lookback window.
    * IT & SI: OEM MAF validation gate and ISO/CMMI/STQC set-difference analysis.
    * Consultants: Consortium matchmaker (Pillar B) to pair MSMEs with EPCs and OEMs.

=== SLIDE 5: Technical Architecture & Stack ===
* PPT Proposed Components:
  - User Experience: Next.js 14, TypeScript, Tailwind CSS.
  - API & Orchestration: FastAPI, Pydantic, Celery async jobs.
  - Web Intelligence: SerpAPI, httpx, TinyFish API.
  - Document Intelligence: PyMuPDF (fitz), IBM Docling (TableFormer).
  - Qualification Engine: Python business rules + Structured LLM outputs.
  - Data & Operations: PostgreSQL, MinIO/S3, Redis, Docker.
* Current Solution Realization:
  - Backend Stack: 100% compliant with FastAPI, Pydantic (contracts/schema.py), PyMuPDF, TinyFish.
  - LLM Upgrade: Upgraded to Google Gemini 3.8 Flash (gemini-3.8-flash) for low-latency clause audit.
  - Architecture Optimization: Rather than requiring heavyweight Celery/Redis background worker 
    infrastructure for Round 2, the team engineered high-efficiency asynchronous FastAPI routines 
    (evaluate_tender_async) and lightweight Supabase Postgres/Auth, reducing deployment friction 
    while preserving sub-5-minute execution.

=== SLIDE 6: TinyFish API Integration Plan ===
* PPT Plan:
  - Stage 1: TinySearch ($0.00/call) for live GeM, BHEL, ICMR tenders.
  - Stage 2: TinyFetch Recursive ($0.00/call) for bilingual markdown and links:true.
  - Stage 3: TinyAgent Stealth SSE ($0.016/step) fallback for JS-gated GeM filters.
  - Safeguards: URL deduplication, depth limit d <= 2, manual upload fallback.
* Current Solution Realization:
  - Built exactly to spec in backend/services/tinyfish_service.py.
  - Safeguards Enforced: Strict cost circuit breaker (max_steps=10, max_duration_seconds=60), 
    country_code="IN", stateless single-hop batching (max 10 URLs), depth limit d <= 2.
  - Resilience Addition: Integrated live Tavily search adapter as an automatic fallback if TinyFish 
    returns empty results or is rate-limited.

=== SLIDE 7: Scalability, Feasibility & GTM ===
* PPT Plan:

  - Scalability: Asynchronous audits, versioned PDF caching, delta alerts on Corrigenda.

5. THE PRECEDENCE DAG RAG ENGINE (v1.0.3 ARCHITECTURAL BREAKTHROUGH)
----------------------------------------------------------------------------------------------------
In the PPT (Slide 2 & Slide 5), the team acknowledged the risk of "outdated rules in corrigenda" 
and proposed preserving document versions.

In v1.0.3, this was engineered into a dedicated Precedence Directed Acyclic Graph (DAG) RAG Engine 
(backend/engine/precedence_rag_engine.py):

  [Rank 1: Latest Corrigendum (Corr N)]
                 |
                 v (supersedes)
  [Rank 2: Earlier Corrigenda (Corr 1..N-1)]
                 |
                 v (supersedes)
  [Rank 3: Buyer Uploaded ATC / RFP PDF]
                 |
                 v (supersedes)
  [Rank 4: Buyer Text-Based ATC Clauses]
                 |
                 v (supersedes)
  [Rank 5: Main Tender / GeM Bid PDF]

Why this matters over standard RAG:
1. Standard Vector RAG retrieves contradictory chunks and hallucinates or averages them out.
2. TenderLens Precedence DAG classifies clauses into Canonical Categories (TURNOVER, EXPERIENCE, 
   EMD, MII, MAF, CERTIFICATIONS, LD, ARBITRATION, PAYMENT_TERMS).
3. Evaluates edges: Lower rank numbers strictly invalidate higher rank numbers.
4. Preserves full audit trail and coordinate provenance (page number and bounding box [x0, y0, x1, y1]).
